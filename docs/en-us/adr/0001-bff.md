# ADR 0001 — One BFF as the browser's only entry

**Status:** accepted

## Context

The Shop page has to list products (from Catalog), quote and place orders (with Orders), and the Admin page needs aggregates and a live event feed. The browser must not talk to the services directly: Catalog should not be exposed, tokens should not reach the browser, and the feed comes from RabbitMQ.

## Decision

A single host, `Orders.Bff`, with two route groups: `/bff/shop` and `/bff/admin`. nginx is the only service that publishes a host port (`:8080`) and serves the pages and `/bff/*` on the same origin, with no CORS. The BFF keeps the session in a cookie (HttpOnly, Secure, SameSite=Strict), requires `X-CSRF` on every request that changes state, requires the `Admin` role on everything under `/bff/admin`, and signs a 5-minute JWT per service (HMAC-SHA256) to call Orders and Catalog. Pass-through routes use YARP; composed routes use typed clients. The live feed is its own non-durable queue per instance on `orders.events`, delivered to the Admin by Server-Sent Events.

The BFF has no database, calculates no price or discount and holds no domain rule; an architecture test keeps it from referencing more than contracts.

## Consequences

- The browser never sees Catalog or the tokens; Orders API stays a domain service, not a catalog proxy.
- Each page gets a tailored contract, at the cost of one more service to deploy and monitor.
- SSE connections are pinned to one BFF instance (see the [sizing](../04-tech-dimensioning.md)).
- The BFF's development sign-in is provisional; the natural place for an identity provider (OpenID Connect and token exchange) is this host.

## Alternatives considered

- **The browser calling Orders and Catalog:** exposes Catalog, needs CORS and tokens in the browser.
- **Orders API playing the BFF:** it would become a catalog proxy and mix the domain model with the view models of two screens.
