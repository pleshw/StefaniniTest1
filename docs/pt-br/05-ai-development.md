# Desenvolvimento assistido por IA

Qual ferramenta de desenvolvimento com IA este projeto usa, por que ela foi escolhida e como é usada em cada fase do ciclo de vida, com links para as evidências (sessões de chat, commits, PRs) de cada fase.

## Ferramenta

| Item | Escolha |
| --- | --- |
| Ferramenta | **Claude Code** (Anthropic), usado no app desktop do Claude (aba Code) e na CLI `claude` |
| Planejamento, arquitetura, revisão | **Claude Opus 5.5** (`claude-opus-5-5`) |
| Implementação etapa por etapa | **Claude Sonnet 5.5** (`claude-sonnet-5-5`) por padrão, uma sessão por etapa ou lote de etapas do guia de execução; as etapas C22–C29 rodaram no Opus 5.5, e a partir da C38 o modelo está no link de cada sessão (veja as [sessões de implementação](#sessões-de-implementação)) |
| Papel do humano | É responsável por todas as decisões, revisa e faz o merge de todos os PRs; a IA nunca faz merge, nunca aprova o próprio PR e nunca mexe nos secrets dos ambientes |

## Por que o Claude Code

- **Trabalha dentro do repositório, não em uma janela de chat.** Ele lê e edita arquivos, executa `dotnet`, `npm`, `docker compose`, `git` e `gh`, e vê a saída real do compilador e dos testes. Uma etapa está concluída quando os comandos passam, não quando a resposta parece correta.
- **Se encaixa no fluxo de uma etapa, um commit, um PR.** O [Guia de execução](02-execution-guide.md) divide o trabalho em 58 etapas pequenas, com testes e comandos de verificação; o Claude Code consegue levar uma etapa da branch até o PR por conta própria, e um humano revisa um diff pequeno.
- **Contexto longo.** O plano, o guia de execução, o guia de revisão e o código afetado cabem em uma única sessão, então cada etapa é conferida com as decisões registradas por escrito, e não com a memória do modelo.
- **Dois modelos para dois tipos de trabalho.** O Opus 5.5 cuida do trabalho ambíguo (requisitos, trade-offs, arquitetura, revisão). O Sonnet 5.5 cuida das etapas totalmente especificadas, de forma mais rápida e mais barata, e é por isso que o [Dimensionamento técnico](04-tech-dimensioning.md) o considera para a implementação.
- **Recursos nativos de revisão e planejamento.** Plan mode para desenhar a solução antes de editar, sub-agents para revisões independentes e os comandos `/code-review` e `/security-review` como primeiro revisor, antes do revisor humano.
- **Sessões compartilháveis.** Toda sessão tem um link, e é assim que este repositório comprova o uso de IA em cada fase (veja [Evidências](#evidências)).

Alternativas consideradas: GitHub Copilot (forte em autocompletar no editor, mais fraco em etapas que envolvem vários arquivos e terminam em um PR verificado) e assistentes só de chat (sem acesso ao build, aos testes ou ao git, então toda resposta precisa ser copiada e conferida manualmente).

## Processo ao longo do ciclo de vida

| # | Fase | Como a IA é usada | Modelo | Resultado |
| --- | --- | --- | --- | --- |
| 1 | Análise de requisitos | Ler o desafio, listar requisitos e critérios de aceite, levantar questões em aberto (moeda, quem cria os pedidos, confirmação, retenção) para decisão humana | Opus 5.5 | Tabela de decisões no [Plano de implementação](01-implementation-plan.md#visão-geral) |
| 2 | Arquitetura e design | Propor e comparar opções (BFF ou não, Wolverine ou MediatR + RabbitMQ.Client, replica set do Mongo), desenhar diagramas, escrever o modelo de dados e o fluxo de idempotência | Opus 5.5 | [Plano de implementação](01-implementation-plan.md) |
| 3 | Divisão do trabalho | Dividir o plano em 58 etapas do tamanho de um commit, cada uma com testes e comandos de verificação, além do prompt reutilizável do agente | Opus 5.5 | [Guia de execução](02-execution-guide.md) |
| 4 | Governança | Redigir princípios de clean code, critérios de PR, bloqueadores, checklists por stack e regras de pipeline | Opus 5.5 | [Guia de code review](03-code-review-guide.md) |
| 5 | Dimensionamento | Dimensionar runtime, esforço por fase, equipe, cronograma e riscos a partir do plano | Opus 5.5 | [Dimensionamento técnico](04-tech-dimensioning.md) |
| 6 | Implementação | Uma sessão por etapa ou lote de etapas: branch, testes primeiro, código, verificação, um commit por etapa, PR | Sonnet 5.5 (Opus 5.5 em alguns lotes) | Commits e PRs `step/Cxx-*` |
| 7 | Testes | Testes escritos antes do código em cada etapa (TDD), gate de cobertura do front-end (80%) aplicado pelo CI, os do .NET ainda pendentes (veja [Qualidade](quality.md)); a IA não pode pular testes nem afrouxar gates | Sonnet 5.5 | Projetos de teste, `web/tests` |
| 8 | Code review | `/code-review` em todo PR antes da revisão humana; o Opus revisa os PRs de Domain, mensageria e segurança; o humano aprova e faz o merge | Opus 5.5 + humano | Comentários no PR |
| 9 | CI/CD | Pipelines escritos como uma etapa (C08) e revisados como código; o gate de deploy nunca é editado sem duas aprovações | Sonnet 5.5 + humano | `.github/workflows/*` |
| 10 | Documentação e release | README, ADRs, runbook e evidências de aceite mantidos atualizados em cada etapa e finalizados na C58 | Sonnet 5.5 | `README.md`, `README-en-us.md`, `docs/pt-br/adr/`, `docs/en-us/adr/` |
| 11 | Apresentação | Rascunhar slides que resumem a arquitetura, as decisões e os diferenciais | Opus 5.5 | `docs/pt-br/presentation/`, `docs/en-us/presentation/` |

### Salvaguardas

- A IA trabalha a partir da documentação escrita; quando uma etapa contradiz o plano ou exige uma decisão que não está registrada, ela para e pergunta (regra no prompt do agente).
- Uma etapa por sessão, para que cada link de sessão corresponda a exatamente um PR.
- A IA não faz merge, não aprova e não altera branch protection, gates de cobertura, analyzers nem secrets.
- Todo PR gerado por IA é de responsabilidade do humano que o abre ([Guia de code review](03-code-review-guide.md#fluxo-de-revisão), etapa 1).
- Todo documento que a IA escreve ou altera é escrito primeiro em `docs/pt-br/` (fonte da verdade) e espelhado em `docs/en-us/` no mesmo commit (regra no `AGENTS.md` e no prompt do agente).
